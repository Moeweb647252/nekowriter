# AI Novel-Writing Projects: Comparative Survey and What NekoWriter Should Learn

**Date:** 2026-10-28
**Question:** 「去网上找几个比较火的AI小说项目，比如 https://github.com/lingfengQAQ/webnovel-writer，看看有什么能取经的地方，汇总一下告诉我」
**Scope:** open-source projects that actually try to write long fiction, with emphasis on long Chinese web serials (`网文`), a single local author, and an author-in-the-loop workflow.

## How to read this report

Every claim about another project is tagged with what kind of evidence it is:

- `[R]` — the project's README or product page (marketing copy included; treat as a claim, not proof).
- `[D]` — a design/architecture/operation document inside the repository (more detailed than the README, still a document, not code).
- `[S]` — I opened the source file and read the implementation.

Star counts and repository metadata were read from the GitHub API on **2026-10-28**. I did not run any of these projects; all "how it works" statements are from their code or docs. Small personal projects are labelled as such; their README claims are not treated as benchmark results.

The evaluation baseline is NekoWriter as it exists today. It already has: append-only agent history, the staged/approved-write mechanism (D-139), canon (entities, relations with one active relation per ordered pair D-143, timeline, memory notes, foreshadowing, change log with revert, proposals), scoped knowledge with hybrid search, per-book and per-role model routing, a next-action engine, an agent panel plus chapter draft pane with a decision dock, event-driven cache invalidation, and a heavy spec/test culture (see [PROJECT.md](../PROJECT.md), [spec/03](../spec/03-agent-runtime.md), [spec/06](../spec/06-canon-memory.md), [DECISIONS.md](../DECISIONS.md)). Anything already in that list is deliberately *not* recommended again.

## Method and limits

- Search terms included `AI 小说 生成 开源`, `AI novel writer agent`, `long-form fiction generation`, `网文 生成 开源`, and GitHub repository searches sorted by stars. I inspected 15+ repositories and kept the 10 with either real architecture or a distinct idea.
- I did not run any project or reproduce its benchmark claims. README claims such as NovelForge's "400 chapters / 1.08M words" and webnovel-writer's "200 万字" are reported as claims, not verified results.
- Star counts are a snapshot and will change; they are used only to indicate relative visibility, not quality.
- For every source-based claim I read the file in the repository at the branch named in the link. Where the README is vague, the report says so (NovelClaw, NovelForge's tests, ai-novel-writing-assistant's production readiness).

## Bottom line

- The ten projects surveyed converge on **state discipline**, not agent count: a fact ledger, plans at several resolutions, deterministic checks where the rules are enumerable, and status derived from artifacts.
- NekoWriter already has the hard parts (canon, staged writes, tiered memory, hybrid search, a strong test culture). The real gaps are **planning at arc scale**, **deterministic continuity/style checks**, and **evidence-based reporting**.
- Top three: (1) continuity engine, (2) AI-tone/repetition gate, (3) evidence-based session report. Skip the fully automatic multi-agent simulators, editable workflow graphs and plugin kernels.

## 2. Convergent patterns

These are the things several independent projects arrive at. Convergence is weak evidence of a real requirement; it is not proof that it fits NekoWriter.

1. **A fact ledger, not a chat transcript.** webnovel-writer makes `.story-system/` (contracts + accepted `CHAPTER_COMMIT` events) the only source of truth and treats `state.json`, `index.db`, `summaries/`, `memory_scratchpad.json` and vectors as derived read-only projections [R: README](https://github.com/lingfengQAQ/webnovel-writer/blob/master/README.md); its architecture doc repeats the same rule [D: docs/architecture/overview.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/docs/architecture/overview.md). novel-studio says "project truth is on-disk artifacts, not chat history" [R: README](https://github.com/Xiaoyangy/novel-studio/blob/main/README.md), and its pipeline phases require artifact evidence before being marked completed [D: docs/architecture.md](https://github.com/Xiaoyangy/novel-studio/blob/main/docs/architecture.md). ainovel-cli stores `Progress`/`Checkpoint`/`Artifact` on disk and rebuilds recovery from them [D: docs/architecture.md](https://github.com/voocel/ainovel-cli/blob/main/docs/architecture.md). NekoWriter already has this property in SQLite: canon is the fact layer and sessions are append-only history. **Already aligned; do not rebuild.**

2. **Plan at several resolutions, and freeze only the near window.** novel-studio freezes whole-book navigation first, then rehearses one arc and seals at most three chapters at a time [R: README](https://github.com/Xiaoyangy/novel-studio/blob/main/README.md); its arc architecture doc describes the seal/promote/render chain [D: docs/project-all-architecture.md](https://github.com/Xiaoyangy/novel-studio/blob/main/docs/project-all-architecture.md). ainovel-cli starts with a "compass" plus two volumes and expands later arcs on demand [R: README](https://github.com/voocel/ainovel-cli/blob/main/README.md); AI_NovelGenerator models an arc explicitly with goal, start/end state, key beats, continuity notes, target chapter count and entity references [S: backend/services/novel/arc_contract.py](https://github.com/YILING0013/AI_NovelGenerator/blob/main/backend/services/novel/arc_contract.py). webnovel-writer ships 卷纲 planning before 章纲 [R: README](https://github.com/lingfengQAQ/webnovel-writer/blob/master/README.md). NekoWriter has a book-level outline document and a per-chapter outline, but no arc/volume layer. **This is the biggest structural gap.**

3. **Deterministic checks do the enumerable work; the LLM does the judgment.** Novel-OS runs a free local continuity engine before its LLM Guardian, with checks for dormant/overdue threads, unresolved foreshadowing, absent characters, dead characters still active, missing chapter files and status drift [S: core/continuity_engine.py](https://github.com/mrigankad/Novel-OS/blob/dev/core/continuity_engine.py); it also detects a "sagging middle" with a deterministic per-chapter movement score [S: core/stall_detector.py](https://github.com/mrigankad/Novel-OS/blob/dev/core/stall_detector.py). novel-studio writes mechanical gate results and deterministic AI-voice red flags, both bound to the body SHA-256 [D: docs/writing-review-workflow.md](https://github.com/Xiaoyangy/novel-studio/blob/main/docs/writing-review-workflow.md). ainovel-cli has a `/diag` report across flow, quality, planning and context, and is explicit that diagnostics never change state [D: docs/architecture.md](https://github.com/voocel/ainovel-cli/blob/main/docs/architecture.md). NekoWriter's review is almost entirely LLM-based. **Gap.**

4. **The author is the only final gate; agents propose.** webnovel-writer v8 states "主控…不代作者批准", and its settle skill requires an explicit author decision before `novel_settle_chapter` [S: v8 packages/bundle/skills/novel-settle/SKILL.md](https://github.com/lingfengQAQ/webnovel-writer/blob/v8/packages/bundle/skills/novel-settle/SKILL.md). NekoWriter's hold/approve + review verdict is already this pattern, with stronger runtime guarantees than most surveyed projects. **Already aligned; this is a differentiator, not a gap.**

5. **Derive progress and completion from evidence; never trust a model's "done".** webnovel-writer v6 has four final states (已完成 / 部分完成 / 需要你处理 / 未完成) and a projection log that locates failed projections [R: README](https://github.com/lingfengQAQ/webnovel-writer/blob/master/README.md); v8 has explicit result cards where "操作成功" does not mean the chapter flow is complete [S: v8 docs/user/result-cards.md](https://github.com/lingfengQAQ/webnovel-writer/blob/v8/docs/user/result-cards.md). ai-novel-writing-assistant documents a "假完成状态" bug: the UI said a stage was ready while its assets were empty, fixed by gating "can enter chapter execution" on actual character/chapter assets [R: README](https://github.com/AsheGeisha/ai-novel-writing-assistant/blob/main/README.md). chinese-novelist's Phase 4 validates file existence and word count before declaring a project complete [S: references/flows/phase4-validation.md](https://github.com/PenglongHuang/chinese-novelist-skill/blob/master/references/flows/phase4-validation.md). NekoWriter's next-action engine is state-derived, but its agent sessions still lack a single evidence-based report card. **Small gap.**

6. **Minimal layered context beats stuffing prior text.** NovelForge keeps a chapter context at roughly 5–6k tokens by extracting working/episodic/semantic memory instead of feeding prior chapters [R: README](https://github.com/xiehuanyi/NovelForge/blob/main/README.md); its memory manager implements the three layers [S: novelforge/memory/manager.py](https://github.com/xiehuanyi/NovelForge/blob/main/novelforge/memory/manager.py). novel-studio uses stage-scoped minimal context and frozen RAG snapshots [R: README](https://github.com/Xiaoyangy/novel-studio/blob/main/README.md). NekoWriter already has tiered memory, frozen kickoffs and context rollover. **Already aligned.**

7. **Package workflow knowledge as procedures/skills, not code.** webnovel-writer v8 ships 11 skills, each a `SKILL.md` with a routing table and an ordered procedure [S: packages/bundle/skills/novel-director/SKILL.md](https://github.com/lingfengQAQ/webnovel-writer/blob/v8/packages/bundle/skills/novel-director/SKILL.md); its `novel-director` skill is a dispatcher that maps Chinese display names to real skill names, calibrates state before acting, and hands prose to subagents rather than writing it, while each node skill declares its artifact paths, author-confirmation gates and an explicit `Off-limits` section [S: novel-outline/SKILL.md](https://github.com/lingfengQAQ/webnovel-writer/blob/v8/packages/bundle/skills/novel-outline/SKILL.md). show-me-the-story embeds Markdown skills such as `story-deslop` and `humanizer-zh` [S: internal/story/embeds/skills/story-deslop.md](https://github.com/Nigh/show-me-the-story/blob/main/internal/story/embeds/skills/story-deslop.md); chinese-novelist is one large skill pack [S: SKILL.md](https://github.com/PenglongHuang/chinese-novelist-skill/blob/master/SKILL.md). NekoWriter has a prompt registry, which covers the *text* side, but no packaged "recipe" layer. This is optional; see §4.

## 3. Ideas worth adopting, ranked

Ranking is by expected value for *NekoWriter's* product (long Chinese web serials, one author, local app) divided by implementation cost. A high-value but large idea can rank below a cheaper one. "Cost" is rough engineering time for this codebase: **S** ≈ 2–5 days, **M** ≈ 2–4 weeks, **L** ≈ 1–2 months including tests and migration.

| # | Idea | Main source(s) | Value | Cost |
|---:|---|---|---|---|
| 1 | Deterministic continuity engine with dismissible findings | Novel-OS, ainovel-cli | High | M |
| 2 | AI-tone and cross-chapter repetition gate (去AI味) | show-me-the-story, novel-studio, ainovel-cli | High | S |
| 3 | Evidence-based session report ("done / partly / needs you / failed") | webnovel-writer, ai-novel-writing-assistant, chinese-novelist | Medium-high | S |
| 4 | Chapter contract: goal, entry/exit state, must/must-not, knowledge boundary | AI_NovelGenerator, webnovel-writer v8, novel-studio | High | M |

| 6 | 追读力 ledger: hooks, cool-points, micro-payoffs, debt | webnovel-writer | High (genre-specific) | M |
| 7 | Consequence preview before accepting an edit | Novel-OS | Medium-high | M (S after #1) |
| 8 | Knowledge-boundary ledger for POV characters | novel-studio, webnovel-writer | Medium | M |

### 1. Deterministic continuity engine with dismissible findings

**From:** Novel-OS [S: core/continuity_engine.py](https://github.com/mrigankad/Novel-OS/blob/dev/core/continuity_engine.py), [S: core/stall_detector.py](https://github.com/mrigankad/Novel-OS/blob/dev/core/stall_detector.py); ainovel-cli [D: docs/architecture.md](https://github.com/voocel/ainovel-cli/blob/main/docs/architecture.md); novel-studio's mechanical gate [D: docs/writing-review-workflow.md](https://github.com/Xiaoyangy/novel-studio/blob/main/docs/writing-review-workflow.md).

**The idea.** Run free, local checks over the canon we already store, before or beside the LLM reviewer. Novel-OS's engine is the clearest precedent: dormant plot threads (idle > 3 chapters), overdue threads (past their target chapter), unresolved foreshadowing, main characters absent > 5 chapters, protagonists who never appear, dead characters with active state, missing chapter files, and "draft exists but status still planned" [S: core/continuity_engine.py](https://github.com/mrigankad/Novel-OS/blob/dev/core/continuity_engine.py). Its `stall_detector` goes further: it counts measurable movement per chapter (plot advances, character development, emotional beats, new information, threads touched) and flags a run of three flat chapters [S: core/stall_detector.py](https://github.com/mrigankad/Novel-OS/blob/dev/core/stall_detector.py). ainovel-cli's `/diag` is a read-only diagnostic layer over the same kind of state [D: docs/architecture.md](https://github.com/voocel/ainovel-cli/blob/main/docs/architecture.md). Neither uses an LLM for the enumerable part.

**What it changes in NekoWriter.** A new `services/continuity.rs` plus one migration for `continuity_dismissals` (or compute findings on read and store only dismissals); a `GET /books/:id/continuity` endpoint; a Canon › Continuity view and an attention row on the overview. The first version should be deliberately small and use only data we already have:

- open foreshadowing planted more than N chapters ago (we have `planted_chapter_id` and `status`);
- an entity with `status = dead/destroyed` that appears in a later chapter (we have `appearances` and `status`);
- the protagonist absent for more than N chapters;
- an active relation whose endpoint is dead;
- an `official` chapter whose `canon_status` is not `synced` (already in the overview, but surface it as a finding);
- an official chapter with no summary / zero words;
- an isolated track's canon referenced from the shared track (or vice versa) if we can detect it cheaply.

Each finding gets a stable key and a "This is intentional" action with a reason, persisted. That dismissal mechanism is not cosmetic: Novel-OS explicitly argues that without it the same false positive is re-raised every run until the author stops reading the panel [R: README](https://github.com/mrigankad/Novel-OS/blob/dev/README.md).

**Why it matters for NekoWriter.** It is the cheapest way to deliver on the core promise "the AI remembers the book" without paying tokens. The data is already curated by the archivist; the checks are pure functions and therefore testable in the existing Rust test style. It also creates the substrate for consequence preview (#7). For a 200万字 serial, the failure mode is not one bad sentence; it is a dead character walking into chapter 180 or a foreshadowing thread silently disappearing for 50 chapters.

**Cost and risk.** **M** — perhaps two to three weeks: one migration, one service with six checks, API, one page/card, tests, i18n. Risk: false positives and noise. Mitigations: start with high-confidence checks only, make every finding dismissible with a reason, never block writing, and keep the reviewer/next-action semantics untouched. Side-track visibility (shared vs isolated canon) needs the same `Visibility` rules as [spec/06 §2](../spec/06-canon-memory.md).

### 2. AI-tone and cross-chapter repetition gate (去AI味)

**From:** show-me-the-story [S: internal/story/embeds/skills/story-deslop.md](https://github.com/Nigh/show-me-the-story/blob/main/internal/story/embeds/skills/story-deslop.md), [S: humanizer-zh.md](https://github.com/Nigh/show-me-the-story/blob/main/internal/story/embeds/skills/humanizer-zh.md); novel-studio [D: docs/writing-review-workflow.md](https://github.com/Xiaoyangy/novel-studio/blob/main/docs/writing-review-workflow.md); ainovel-cli [D: docs/voice-layer.md](https://github.com/voocel/ainovel-cli/blob/main/docs/voice-layer.md); webnovel-writer [S: agents/reviewer.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/webnovel-writer/agents/reviewer.md).

**The idea.** A deterministic text-quality pass for the specific smells of machine-written Chinese prose. show-me-the-story has the most concrete public artifact: six gates with actual thresholds — e.g. "宛如/犹如/仿佛 > 2 per 1,000 characters → FAIL", "微微/缓缓/徐徐/悄然 > 3 per 1,000", "连续 3 句以上使用『主语+说道』", "连续 3 段以人名开头", "段落平均长度偏差 < 20 %", "模板化表情 > 3 per 1,000" — plus a large replacement table (`宛如 → 好像`, `瞳孔微缩 → 一愣`, `心中暗道 → 直接写心理`) [S: story-deslop.md](https://github.com/Nigh/show-me-the-story/blob/main/internal/story/embeds/skills/story-deslop.md). novel-studio goes further with deterministic AI-voice red flags and an AIGC ratio gate: target ≤ 5 %, `aigc_ratio >= 35%` is blocking [D: docs/writing-review-workflow.md](https://github.com/Xiaoyangy/novel-studio/blob/main/docs/writing-review-workflow.md). ainovel-cli's "Voice Layer" lets the author override style and anti-AI rules without changing code [D: docs/voice-layer.md](https://github.com/voocel/ainovel-cli/blob/main/docs/voice-layer.md). NekoWriter's reviewer prompt already lists "AI 腔" as a prose dimension [S: prompts/system.toml](../../prompts/system.toml), but that is one LLM judgment per chapter, not a repeatable check.

**What it changes in NekoWriter.** A `services/style_check.rs` with pure functions and a versioned built-in Chinese phrase list; `GET /chapters/:id/style-check` plus a "Style" card inside the Review tab. First version: four gates — high-frequency AI words, repeated sentence-opening patterns, paragraph-length uniformity, and template expressions — plus an 8-gram overlap check against the previous 10 official chapters (this is the "serial style memory" part of novel-studio [R: README](https://github.com/Xiaoyangy/novel-studio/blob/main/README.md), and it is genuinely different from an LLM's impression). Findings point at paragraph ids (`pid`) and quoted spans, so the existing diff/quote UI can show them. It should be advisory, not blocking; the author decides. A later optional "Polish" action could feed the findings into a revision prompt.

**Why it matters for NekoWriter.** This is the most genre-specific quality problem in Chinese web fiction, and the one readers punish immediately. It is also the kind of check that gets *worse* when delegated to an LLM reviewer: the model will happily use the same clichés it is supposed to flag. A local, deterministic gate is cheap, fast and explainable.

**Cost and risk.** **S** — about one week for the checker, endpoint, card and tests; the phrase list is content work that can grow. Risk: false positives ("缓缓" is sometimes the right word), genre differences, and over-correction into flat prose. Keep thresholds configurable, show the count rather than a single "AI score", and never block approval. A hard AIGC-ratio threshold from novel-studio would be wrong for us: it is a fully automatic production gate, while our author may deliberately want a plain style.

### 3. Evidence-based session report ("done / partly / needs you / failed")

**From:** webnovel-writer v6's four final states [R: README](https://github.com/lingfengQAQ/webnovel-writer/blob/master/README.md) and v8's result cards [S: docs/user/result-cards.md](https://github.com/lingfengQAQ/webnovel-writer/blob/v8/docs/user/result-cards.md); ai-novel-writing-assistant's "假完成状态" fix [R: README](https://github.com/AsheGeisha/ai-novel-writing-assistant/blob/main/README.md); chinese-novelist's Phase 4 validation [S: references/flows/phase4-validation.md](https://github.com/PenglongHuang/chinese-novelist-skill/blob/master/references/flows/phase4-validation.md).

**The idea.** After a long agent run, give the author one card that answers "what actually happened, what is left, what needs me" — computed from persisted facts, not from the model's closing sentence. webnovel-writer's four states are exactly the right vocabulary: 已完成 (artifacts and key checks pass), 部分完成 (main artifact kept but skipped/auto-handled items remain), 需要你处理 (system stopped safely and needs a creative/factual/file decision), 未完成 (key artifact not trustworthy). v8's result cards add the important nuance that a successful tool call is not a completed chapter flow. ai-novel-writing-assistant's bug is the cautionary tale: a stage said "ready" while its assets were empty, so the fix was to gate the next stage on actual assets [R: README](https://github.com/AsheGeisha/ai-novel-writing-assistant/blob/main/README.md).

**What it changes in NekoWriter.** A `SessionReport` DTO computed in `services/sessions.rs` from persisted state: session kind/status, finish reason, tool errors, chapter status and `content_version`, `canon_status`, open proposals, review verdict, word count vs. target, and warnings. Four states map to `completed / partial / needs_author / failed`. `GET /sessions/:id/report`; render the card at the top of the agent panel after completion and link it from the overview's attention list. No migration; no new prompt; the model never writes the report.

**Why it matters for NekoWriter.** A writer session can run for dozens of tool calls and then end in `completed` with a chapter that is still `in_review` and canon still `pending`. The status is technically true and practically useless. This card is the missing "receipt" for the author and directly prevents "假完成" in our UI. It is also the right place to surface `warnings: ["context.large_kickoff"]` or a failed projection/index job.

**Cost and risk.** **S** — three to five days. Risk: mapping every session kind and transition correctly; the report must be derived from evidence, not model claims, and should not become a second status system. Reuse the existing `SessionDto`/event invalidation so it never goes stale (the D-144 lesson).

### 4. Chapter contract: goal, entry/exit state, must/must-not, knowledge boundary

**From:** AI_NovelGenerator [S: backend/services/novel/chapter_contract.py](https://github.com/YILING0013/AI_NovelGenerator/blob/main/backend/services/novel/chapter_contract.py); webnovel-writer v8 [S: packages/bundle/skills/novel-outline/SKILL.md](https://github.com/lingfengQAQ/webnovel-writer/blob/v8/packages/bundle/skills/novel-outline/SKILL.md); novel-studio [D: docs/project-all-architecture.md](https://github.com/Xiaoyangy/novel-studio/blob/main/docs/project-all-architecture.md).

**The idea.** A chapter plan should be more than a Markdown outline. AI_NovelGenerator's `ChapterPlanV2` is a practical, already-shipped schema: `goal`, `start_state`, `end_state`, `beats[]`, `pov_character_id`, `must_include[]`, `must_avoid[]`, `target_word_count` [S: chapter_contract.py](https://github.com/YILING0013/AI_NovelGenerator/blob/main/backend/services/novel/chapter_contract.py). webnovel-writer v8's outline skill asks for a nine-section positioning block — source window, chapter function, POV and focus, time/space anchor, start/end boundary, storyline and promise allocation, **information boundary**, emotional/pace target, precondition check — followed by narrative units with six fields and explicit `〔硬〕/〔软〕/〔自由〕` tags [S: novel-outline/SKILL.md](https://github.com/lingfengQAQ/webnovel-writer/blob/v8/packages/bundle/skills/novel-outline/SKILL.md). novel-studio's sealed chapter plan is the same idea under a stricter regime: a chapter cannot be promoted until its predecessor's exit state equals its entry state, and the sealed plan is immutable [D: docs/project-all-architecture.md](https://github.com/Xiaoyangy/novel-studio/blob/main/docs/project-all-architecture.md).

**What it changes in NekoWriter.** Add an optional `chapter_contract` to the chapter (new JSON column or `chapter_contracts` table with `version` and `status`). Keep the existing free-text `outline` as a fallback; the contract is what the writer submits through `submit_outline` when enabled. Fields: `goal`, `pov_entity_id`, `start_state`, `end_state`, `must_include[]`, `must_avoid[]`, `knowledge_boundary` (what the POV knows / must not know), `beats[]`, `target_words`. The author can edit and approve it exactly like the current outline. The reviewer receives it as structured data and checks contract compliance; maintenance can compare the actual end state with the declared `end_state`; the next chapter's `start_state` can prefill from the previous `end_state`. This is not a second canon: `start_state`/`end_state` are declared expectations, while canon remains the observed truth.

**Why it matters for NekoWriter.** NekoWriter's current outline is free-form `TEXT` ([spec/02 §2](../spec/02-data-model.md)); the reviewer must infer "what was supposed to happen" from prose. For long serials the hard part is not plot events but state in/out and who knows what. A contract makes those checkable at the exact boundary where drift enters. AI_NovelGenerator's schema is evidence that authors and models can work with these fields; we do not need to invent a taxonomy.

**Cost and risk.** **M** — three to four weeks: schema, DTO, prompt changes, UI form in the Outline tab, reviewer kickoff block, tests and migration. Risk: over-formalization and author friction. Ship it optional and read-only first (the writer fills it; the author sees it; no gate), then let the author require it per book. Do not copy novel-studio's three-chapter sealed rehearsal; our product approvals are per chapter.

### 5. Arc/volume plan with a rolling compass

**From:** novel-studio [R: README](https://github.com/Xiaoyangy/novel-studio/blob/main/README.md) + [D: docs/project-all-architecture.md](https://github.com/Xiaoyangy/novel-studio/blob/main/docs/project-all-architecture.md); ainovel-cli [R: README](https://github.com/voocel/ainovel-cli/blob/main/README.md) + [D: docs/architecture.md](https://github.com/voocel/ainovel-cli/blob/main/docs/architecture.md); AI_NovelGenerator [S: backend/services/novel/arc_contract.py](https://github.com/YILING0013/AI_NovelGenerator/blob/main/backend/services/novel/arc_contract.py), [S: backend/services/novel/volume_service.py](https://github.com/YILING0013/AI_NovelGenerator/blob/main/backend/services/novel/volume_service.py); webnovel-writer's 卷纲 planning [R: README](https://github.com/lingfengQAQ/webnovel-writer/blob/master/README.md).

**The idea.** The convergent answer to "how do you plan 300 chapters without writing a dead outline" is: keep a compass (ending direction + active long lines + scale estimate), plan only the next volume/arc in detail, and expand just in time. novel-studio freezes whole-book navigation, then rehearses one arc and seals at most three chapters [R: README](https://github.com/Xiaoyangy/novel-studio/blob/main/README.md); ainovel-cli starts with two volumes and the first arc, then lets the Architect expand [R: README](https://github.com/voocel/ainovel-cli/blob/main/README.md); AI_NovelGenerator has a real `ArcPlanningV1` with `goal`, `start_state`, `end_state`, `key_beats`, `continuity_notes`, `target_chapter_count`, `target_word_count` and entity references [S: arc_contract.py](https://github.com/YILING0013/AI_NovelGenerator/blob/main/backend/services/novel/arc_contract.py).

**What it changes in NekoWriter.** Add `volumes` and `arcs` as data objects ([PROJECT §9.2](../PROJECT.md) currently excludes them — this would be a deliberate post-MVP scope change), plus a `compass` JSON on the book: ending direction, open long lines, estimated scale. A new "Plan" tab in the book workspace shows compass → volumes → current arc → chapter range. The overview's next-action engine gets a `plan_next_arc` action when the current arc is exhausted or missing. The writer's kickoff gets the current arc's goal, entry/exit state and key beats as stable context. Conception seeds volume 1 and the first arc, not a 300-chapter outline.

**Why it matters for NekoWriter.** This is the largest structural gap. NekoWriter's conception writes one outline document and each chapter plans itself; that is fine for 30 chapters and fragile at 200万字. The product promise is a long serial, and long serials need a middle layer between "the book's direction" and "this chapter's scenes". The "thin" version is still useful: an arc is a Markdown document plus a chapter budget and a next-action gate.

**Cost and risk.** **L** for a real implementation (new tables, service, API, Plan UI, prompts, migration, tests); **M** for a thin version that stores arc documents and prompts the author to plan the next one. Risk: scope creep against MVP §9.2, overplanning that kills discovery, and a second plan that disagrees with the setting `outline` document. Mitigation: make the arc plan the only structured plan, keep it editable, and let the author skip it. Do not copy novel-studio's automatic character-agent rehearsal.

### 6. 追读力 ledger: hooks, cool-points, micro-payoffs, debt

**From:** webnovel-writer [S: webnovel-writer/references/reading-power-taxonomy.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/webnovel-writer/references/reading-power-taxonomy.md), [S: webnovel-writer/skills/webnovel-write/references/writing/genre-hook-payoff-library.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/webnovel-writer/skills/webnovel-write/references/writing/genre-hook-payoff-library.md); reviewer's Reader-pull Checker [S: agents/reviewer.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/webnovel-writer/agents/reviewer.md); README says the system was introduced in v5.3 [R: README](https://github.com/lingfengQAQ/webnovel-writer/blob/master/README.md).

**The idea.** Treat reader retention as data, not a vibe. webnovel-writer's taxonomy defines hook types (危机钩, 悬念钩, 渴望钩, 情绪钩, 选择钩), strength levels, cool-point patterns (装逼打脸, 扮猪吃虎, 越级反杀, 打脸权威, 反派翻车, 甜蜜超预期, 迪化误解), micro-payoffs, and "debt" tracking [S: reading-power-taxonomy.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/webnovel-writer/references/reading-power-taxonomy.md). Its per-genre library gives chapter-end hook and micro-payoff examples for esports, livestream and cosmic horror [S: genre-hook-payoff-library.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/webnovel-writer/skills/webnovel-write/references/writing/genre-hook-payoff-library.md). The reviewer includes a Reader-pull Checker dimension [S: agents/reviewer.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/webnovel-writer/agents/reviewer.md).

**What it changes in NekoWriter.** A `chapter_beats` record — either a JSON column on the chapter or a small table — with `hook_type`, `hook_strength`, `cool_point_type`, `micro_payoffs[]`, `debts_opened[]`, `debts_closed[]`, and `reader_promise`. The archivist fills it after chapter approval (it already reads the chapter); the author can edit it. A "Retention" card in the Review tab shows the current chapter's hooks/payoffs; the overview shows a small strip of recent hook types and open debts. The writer's kickoff gets the last three hook types and open debts so it can avoid repetition. Start with 5 hook types, 3 cool-point types and 4–6 genre profiles — not all 37 templates.

**Why it matters for NekoWriter.** Chinese web novels live on serialized retention: the reader must want the next chapter. NekoWriter has foreshadowing with `planned_payoff` ([spec/06 §1.5](../spec/06-canon-memory.md)), which is a *plot* promise, not a *reader-experience* promise. A hook/payoff ledger is the missing feedback loop, and it is exactly the kind of genre knowledge that is hard to keep in an author's head across 200 chapters.

**Cost and risk.** **M** — about three weeks: schema/JSON, maintenance prompt, review card, overview strip, tests. Risk: formulaic writing and taxonomy fatigue; an author who does not want to tag every chapter will ignore it. Mitigation: make it optional, auto-fill from the archivist, surface only 2–3 signals per chapter, and never turn it into a score or a gate.

### 7. Consequence preview before accepting an edit

**From:** Novel-OS [S: core/consequence.py](https://github.com/mrigankad/Novel-OS/blob/dev/core/consequence.py) and [R: README](https://github.com/mrigankad/Novel-OS/blob/dev/README.md).

**The idea.** When the author rewrites a passage, show what the rewrite breaks *before* accepting it. Novel-OS's implementation is deliberately split: it dry-applies a state delta and diffs the deterministic continuity findings before/after ("ripple"), while anything the model invents outside the engine is labelled *predicted*, not fact [S: core/consequence.py](https://github.com/mrigankad/Novel-OS/blob/dev/core/consequence.py). The README describes the user-facing version: rewrite a passage and see what it breaks before accepting [R: README](https://github.com/mrigankad/Novel-OS/blob/dev/README.md).

**What it changes in NekoWriter.** Once #1 exists, a `POST /chapters/:id/preview-edit` (and later `POST /proposals/:id/preview`) that:
1. takes the proposed text or a selected range replacement;
2. computes the affected entities/terms via the existing canon index;
3. dry-applies a state-delta proposal (initially by asking the archivist for a diff, or by a cheap rule-based extraction for names/items);
4. runs the continuity checks before and after and returns the new findings, plus the canon records that mention the changed terms.

The UI belongs in the decision dock and the outline/proposal diff view: "This edit would leave 2 open foreshadowing threads pointing at the old wording" etc. Do not auto-apply anything; the author still approves.

**Why it matters for NekoWriter.** Author-in-the-loop editing is the product's core. Right now change log + revert are *after the fact*; a preview is *before*. The decision dock already exists (D-139/D-141/D-144), so the UX surface is there; the missing piece is the analysis.

**Cost and risk.** **M** initially (the extraction is the hard part), **S** once #1 is solid and v1 only reports deterministic findings + affected records. Risk: false positives and information overload; an LLM-extracted delta can be wrong. Label deterministic findings and predicted consequences separately, as Novel-OS does, and let the author dismiss.

### 8. Knowledge-boundary ledger for POV characters

**From:** novel-studio [S: internal/agents/character_agents.go](https://github.com/Xiaoyangy/novel-studio/blob/main/internal/agents/character_agents.go); webnovel-writer's reviewer checklist [S: agents/reviewer.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/webnovel-writer/agents/reviewer.md); NekoWriter's own memory-note model [D: spec/06 §1.5](../spec/06-canon-memory.md).

**The idea.** In novel-studio, a character agent only receives a `character_observation_packet`, and `knowledge_refs` can only quote fact ids present in that observation; secrets and future outlines never reach the character [S: internal/agents/character_agents.go](https://github.com/Xiaoyangy/novel-studio/blob/main/internal/agents/character_agents.go). The World Arbiter decides outcomes but cannot rewrite intentions [S: internal/agents/character_agents.go](https://github.com/Xiaoyangy/novel-studio/blob/main/internal/agents/character_agents.go). That is a heavy simulation architecture. The narrow, useful part for NekoWriter is a *knowledge ledger*: for each secret/identity/relationship reveal, who knows it, who must not, and when it becomes known. NekoWriter's memory notes already allow facts like "苏婉不知道林凡的真实身份" [D: spec/06 §1.5](../spec/06-canon-memory.md), and the reviewer prompt lists "角色知识边界" in webnovel-writer [S: agents/reviewer.md](https://github.com/lingfengQAQ/webnovel-writer/blob/master/webnovel-writer/agents/reviewer.md), but we have no structured query for it.

**What it changes in NekoWriter.** Extend memory notes with optional `known_by` / `unknown_by` / `revealed_chapter_id` arrays (or a dedicated `knowledge_facts` table), surfaced on the entity page as "Who knows what". The writer kickoff's `block.memory` gets a POV-specific knowledge block: facts the POV knows, facts they must not act on yet, and facts scheduled to be revealed. The reviewer gets a "knowledge boundary" dimension backed by that list.

**Why it matters for NekoWriter.** Secrets, hidden identities, misunderstandings and delayed reveals are a staple of long Chinese serials, and "a character acts on information they could not know" is a classic long-range error. The LLM reviewer can only catch it if the relevant facts happen to be in context; a ledger makes it explicit.

**Cost and risk.** **M** — three weeks: schema, archivist extraction rules, memory snapshot changes, reviewer prompt, entity UI, tests. Risk: bookkeeping burden and wrong extraction; a wrong `known_by` is worse than no ledger. Start by letting the archivist propose entries and the author confirm them, not by auto-enforcing.

### Smaller wins worth doing while touching the above

- **Book-level token budget (S).** NekoWriter already records usage per session and the overview has a token total ([spec/08 §7](../spec/08-workflows.md)); add a per-book `token_budget` in `BookSettings` with a warning and a soft stop before a new model step. Do not add currency price tables — [PROJECT §9.2](../PROJECT.md) explicitly excludes them and prices go stale. novel-studio's `budget.book_usd` [D: config.example.jsonc](https://github.com/Xiaoyangy/novel-studio/blob/main/config.example.jsonc) is the full version; our token version gets most of the safety for a fraction of the work.
- **Model-switch retry from the last checkpoint (S).** ai-novel-writing-assistant lets the author switch the model in the task center and retry from the most recent checkpoint [R: README](https://github.com/AsheGeisha/ai-novel-writing-assistant/blob/main/README.md). NekoWriter freezes a model snapshot per session, so a failed session currently means starting a new one; a "retry with another model" that creates a child session with the same kickoff would be a small, useful recovery path. Only offer it for `failed`/`interrupted` sessions, and keep the original session as history.
- **A "doctor" page/CLI (S).** webnovel-writer has `/webnovel-doctor` and `preflight` [R: README](https://github.com/lingfengQAQ/webnovel-writer/blob/master/README.md); ainovel-cli has `/diag` [D: docs/architecture.md](https://github.com/voocel/ainovel-cli/blob/main/docs/architecture.md); novel-studio has `--diag` and `doctor` [R: README](https://github.com/Xiaoyangy/novel-studio/blob/main/README.md). For NekoWriter, a read-only check of provider connectivity, embedding model state, prompt validation, orphaned sessions, index health and DB integrity would turn support questions into a screen. Low urgency; pair it with #1.
- **Genre profile seeds (S).** Instead of porting 37 templates, ship 4–6 profiles (玄幻/修仙, 都市, 言情, 悬疑/规则怪谈) as knowledge-base entries with hook/pacing guidance, and let the conception agent cite them. This is content, not code, and it complements #6.

## 5. The three things I would do first

1. **Ship the deterministic continuity engine (#1).** It is the highest-value thing that costs no tokens, it uses canon we already trust, and it is the foundation for consequence preview later.
2. **Ship the AI-tone/repetition gate (#2).** It is a one-week, local, explainable check for the single most visible quality problem in Chinese web fiction, and it complements rather than duplicates the LLM reviewer.
3. **Ship the evidence-based session report (#3).** It is cheap, it removes the "假完成" trust gap in long agent runs, and it makes every later feature (arc planning, 追读力, consequence preview) easier to explain to the author.

The first structural bet after those three should be the **chapter contract (#4)**, because it is the smallest change that makes long-range state auditable; the **arc plan (#5)** is the largest strategic gap but should not start until the chapter-level contract proves the author will use structured plans.
