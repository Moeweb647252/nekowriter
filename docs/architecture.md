# Architecture

This document explains how NekoWriter is built and why. It is for maintainers. What the product does is specified in [`product-spec.md`](product-spec.md); § numbers refer to its sections, and "section N" to this document's.

## 1. Principles

1. **One definition per concept.** A domain type is declared once, in `nekowriter-core`. It derives every representation it needs: JSON through serde, SQLite columns through SeaORM (`DeriveActiveEnum`, `DeriveValueType`, `FromJsonQueryResult`), and TypeScript through ts-rs. The generated TypeScript in `webui/src/api/generated/` is regenerated by `cargo test` and checked for freshness by CI. The database, the HTTP API and the web UI cannot drift apart. States that only the store uses, such as tool-call and index-task statuses, are store-local enums.
2. **Errors and outcomes are data.** Core and store return typed enums with structured fields; prose is produced only at an edge, in its audience's language (principle 3). `Display` texts are English and exist for logs.
3. **Each audience's text has one owner.**

   | Audience | Owner | Language |
   |---|---|---|
   | Developers: code, comments, logs, `Display` | the code | English |
   | Users: UI, error messages, enum labels, placeholder help | `webui/src/locales/{en,zh-CN}/` | the interface language |
   | Models: prompts, tool schemas, tool results, corrections, fold rendering | `crates/nekowriter-agent/resources/` | Chinese; the novel's language comes from `{{writing_language}}` |
   | Exported novels: header, chapter labels, draft markers | `crates/nekowriter-app/resources/export/` | the work's writing language |

   The backend sends codes and data, never user-facing prose. `crates/nekowriter-app/tests/english_only.rs` fails on non-English text outside these resource directories.
4. **Every agent run has the same shape.** Preparation, outline and body writers and review agents run in rounds: a request, an answer with one tool call, and the call's outcome as the next request's tool result. What differs per stage is data (section 4).
5. **Correct by construction.** Every user write goes through an idempotent command (section 6). State and its events commit in one transaction. Clippy pedantic runs with `-D warnings`, and `unsafe` is forbidden.
6. **No compatibility layers.** The schema is created from the entities and checked by fingerprint (section 8); there are no migrations, backfills or fallbacks.

## 2. Crates

Each arrow points from a crate to a crate it depends on:

```text
nekowriter-app -> nekowriter-store -> nekowriter-core
nekowriter-app -> nekowriter-agent -> nekowriter-core
```

- **`nekowriter-core`** has no I/O. It holds identifiers and validated text fields (`field.rs`), the workflow and run state (`workflow.rs`, `run.rs`), tool calls and their outcomes (`call.rs`, `run_message.rs`), submissions and their checks (`submission.rs`, `preparation.rs`), reviews, questions, feedback and citations, body edits (`body.rs`), the restricted template engine (`template.rs`), prompt keys and their variables (`prompt.rs`), and knowledge, embeddings, usage, dashboard buckets and engine contracts.
- **`nekowriter-store`** is the only way to read and write the database. Its modules follow the product: `projects`, `versions`, `preparation`, `chapters`, `execution` (runs and requests), `calls` and `tools` (tool calls), `feedback`, `proposals`, `questions`, `reviews`, `delegation`, `citations`, `prompts`, `templates`, `knowledge`, `indexing`, `search`, `embedding`, `dashboard` and `export`. Entities live in `entity/` and never leave the crate; queries return view types.
- **`nekowriter-agent`** owns the model protocol: the Chat Completions client (`client.rs`), the embeddings adapter (`embedding.rs`), stage contracts and tools (`stage.rs`), argument schemas (`schema.rs`), answer classification (`round.rs`), request assembly and the context limit (`context.rs`), rendering of stored outcomes into model text (`render.rs`), the built-in prompts (`prompts.rs`), the model text (`model_text.rs`) and the engine registries (`engines.rs`). It stores nothing and decides nothing about approvals.
- **`nekowriter-app`** wires everything: startup and shutdown (`lib.rs`, `lifecycle.rs`), the HTTP API and the embedded web UI (`http/`), the event stream, the dispatcher (`dispatcher.rs`), the indexer (`indexer.rs`), knowledge search shared by the page and the agents (`knowledge_search.rs`), streaming previews (`preview.rs`) and export (`export.rs`).
- **`webui`** is React 19 with TanStack Query, react-router, i18next, Tailwind and shadcn components on Base UI. Pages live in `src/features/<area>/`; the API layer is `src/api/` (`endpoints/` for calls, `queries/` for hooks and query keys, `events/` for the event stream, `generated/` for types).

## 3. Workflow and runs

A version has two state axes (§5).

- **Workflow** (`WorkflowStage`): `preparation{step}` → `chapter{chapter_id, step}` per chapter → `completed`. Preparation steps are `not_started`, `generating`, `reviewing` and `revising`. Chapter steps are `ready`, `outline_generating`, `outline_reviewing`, `drafting`, `reviewing` and `done`. Extra chapters reuse the chapter steps after completion.
- **Execution** (`RunStatus`) is the version's active run: `queued`, `running`, `waiting_review`, `paused`, `waiting_answer`, `interrupted`, `stopped`, `failed` or `succeeded`. Runs have a kind: `preparation`, `chapter_outline`, `chapter_body` or `review`. Review runs are children of the run whose submission they decide; they never hold a project's writing slot and are never continued.

Transitions live where they are decided: submissions in `store::calls::execute` and the per-stage `apply_*` functions, reviews in `store::reviews` and the kind-specific `decide_*` functions, and folds in `store::workflow`. Each check returns a typed `StateConflict` when a command does not fit the current state.

Tool calls have their own small state machine (`entity/tool_call.rs`):

- `received`: a call that just arrived is carried out in the same transaction, or held.
- `held`: a paused run holds the call until the user continues.
- `awaiting_review`: a proposed edit in ApproveRequired mode.
- `awaiting_answer`: an `ask_user` call waits for answers.
- `executing`: a knowledge query waits for the dispatcher.
- `resolved`: the outcome is stored, and its result message waits for the next request.

User feedback is `queued`, then `bound` to the result of a later call, then `included` in the request that carries it (§9.2).

## 4. The stage contract, and how to add a flow

Every model-driven stage is described by data:

- **agent** (`stage.rs`): `build(input, language, prompts, available)` returns the rendered system and user prompts and a `Contract`: the stage's work tools and exactly one submission tool. The tool's JSON schema, the argument parser and the contract text in the system prompt come from the same definitions. `prompt_key` names the stage's prompt pair.
- **core**: the stage's input (`StageInput`), the parsed submission (`StageSubmission`) and its business checks (`submission.rs`).
- **store**: the stage input is assembled from stored data (`execution::dispatch_input`, `delegation::review_subject`), and accepting a submission is one transition (`apply_submission`, `apply_outline_submission`, `apply_chapter_submission`, `apply_verdict`).
- **app**: the dispatcher's round is generic; nothing in it is per stage.

To add a flow:
1. Add its `StageInput` and `StageSubmission` variants in core.
2. Add a `RunKind` and, if it changes the workflow, its steps.
3. Add its prompt pair under `resources/prompts/` and its `PromptKey`.
4. Add a `build` arm and a submission tool in the agent.
5. Add the input assembly and an `apply_*` transition in the store.
6. Write the spec section first, then a store test and an app test with the scripted model (`crates/nekowriter-app/tests/common/model.rs`).

To add a work tool, add a `WorkTool` variant with its definition and parser, and a `CallRequest` variant. Then handle the request in `store::calls::execute`. A tool that needs the network does not run there: `execute` marks the call `executing`, and `store::tools` and the dispatcher carry it out between rounds, as `query_knowledge` does (section 7). Then render its `ToolOutcome` in `render::tool_outcome`.

## 5. The dispatcher and the sealing point

`app::dispatcher` is one task: it sends one model request at a time, which is the global model permit (§8.2). It serves the oldest queued run. A round:

1. **Executing tools first.** `Store::begin_tool` resolves or charges a waiting knowledge query. The dispatcher searches and records the outcome with `finish_tool` (section 7).
2. **Input.** `Store::dispatch_input` reads the latest settings, the effective prompts, the searchable knowledge spaces, the folds of completed stages, and the run's conversation. The conversation holds messages that were sent, plus messages still pending (tool results, review outcomes, corrections).
3. **Prepare.** The agent builds the stage, renders the pending messages once, assembles the request and checks it against the model's input budget. A request that does not fit fails the run with `context_limit_exceeded`; artifacts are never truncated (§11).
4. **Seal.** `Store::dispatch` stores the rendered pending messages, includes the feedback bound to them, counts the request against the run's allowance and marks the run running, in one transaction. It refuses when a newer message or feedback arrived since step 2, and the round starts over. Sent history is therefore never rewritten, and feedback is delivered exactly once, with the result it was bound to.
5. **Stream.** The answer streams from the model service. Text and tool-call deltas are published as previews; they are ephemeral and never part of the event log.
6. **Classify and record.** `round::classify` turns the answer into one valid call or a protocol error with its correction. `Store::record_answer` stores the assistant message and usage, then carries out, holds or proposes the call. Every store step re-checks the run, so a run that was stopped meanwhile is never advanced by a late answer.

Store errors during a round fail the run with the halt reason `internal`. Provider failures fail it with `provider`. Both keep everything committed so far.

Folds (§11) are rebuilt for every request from the approved revisions. They are sent as one assistant message after the system prompt, so earlier folds stay a stable prefix.

The **indexer** (`app::indexer`) is a second task for knowledge embeddings (section 11). Both tasks wake on committed events through the store's watch channel.

## 6. Commands, events and the HTTP API

**Commands.** Every user write is a command identified by a `CommandId` that the client creates per user action and reuses on retry (`webui/src/api/command.ts`). `Store::begin_command(id, kind, input)` either replays the stored outcome of an earlier attempt, or opens a `CommandTx`. The input is hashed, so reusing an ID with different input is an `IDEMPOTENCY_CONFLICT`. Committing writes the data, the receipt and the events in one transaction. Commands on a resource quote its revision (a project's, the settings', a template's, a version's workspace revision). Control commands, which apply while an agent advances the workspace, quote none: stop, feedback, pause, resume, approval mode, answers and delegation cancellation.

**Events.** `nekowriter_core::event::Event` says what changed (a project, a version's workspace, the settings, templates, the knowledge base), never the new state. Events are appended in the transaction that makes the change and kept for 7 days. A client reads the cursor (`/api/events/cursor`), loads its data, then subscribes to `/api/events?after=<cursor>`; a reconnecting browser resumes with `Last-Event-ID`. A cursor outside the log gets a `reset_required` message, and the client reloads. Previews share the stream without a sequence number. In the web UI, `api/events/invalidation.ts` maps each event to the TanStack Query keys it invalidates. The switch is exhaustive, so a new event cannot be forgotten.

**HTTP.** Routes are grouped by area in `app::http::router`. Reads are `GET`, writes are `POST`. A trust gate admits writes only with a loopback `Host` and, when present, an allowed `Origin`: the app itself and the Vite dev server.

## 7. Auxiliary tools and budgets

`query_knowledge` is declared to the preparation and outline writers only when semantic search is ready and a space exists; its schema restricts space names to the live spaces. Because a search needs the network, `calls::execute` only marks the call `executing` and requeues the run. Before the run's next request, `Store::begin_tool` decides, in one transaction, whether the call runs:
- unavailable search, an invalid query, spaces deleted since and an empty budget resolve the call at once, uncharged;
- otherwise the call is charged to its budget scope and handed to the dispatcher.

A scope is the version's preparation, or a chapter's outline. A charge is one row keyed by the call's ID, so it happens once per call. The limit is the project's `auxiliary_budget`, read fresh every time. A query interrupted after its charge runs again without a second charge.

The research and accumulation engine registries (`agent::engines`) hold no engines in this build. `GET /api/engines` reports each empty list with the reason `none_registered`.

## 8. Schema policy

The entities in `store/src/entity/` are the schema. On first start, `store::schema::prepare` creates every table from them in one transaction. It stores a fingerprint of the DDL, plus `FORMAT_REVISION`, which is bumped when the meaning of stored data changes without a DDL change. Any other database is refused before anything is read or changed. The startup error names the data directory, both versions and the next steps. There are no migrations: a development database is recreated when the schema changes.

SQLite runs with foreign keys on, WAL, `synchronous=FULL` and a busy timeout. Deletes of user content are soft (`deleted_at`), and queries check live ancestors.

## 9. Error model

- Core validation returns `FieldError { field, problem }`, template checks return `TemplateError`, and state checks return `StateConflict`. Domain-specific problems (answers, citations, embeddings, search availability) have their own enums.
- `StoreError` wraps them, adds `NotFound`, `RevisionConflict`, `IdempotencyConflict`, `ModelNotReady`, `Database` and `Corrupt`. `Corrupt` marks broken invariants and is never a fallback.
- `app::http::error::ApiProblem` is the one enum the API speaks. It is serialized as `{code, params, requestId}` with 422 for invalid input, 409 for conflicts, 404 for missing resources, and 502/504 for model or embedding service failures. The cause is logged in English under the request ID.
- The web UI turns every code into a sentence in `i18n/errors.ts`. The catalog type is derived from the generated `ApiProblem`, so a new code fails type checking until both languages have a message.

## 10. Model text and prompts

Model-facing text lives in `crates/nekowriter-agent/resources/`:
- `prompts/<key>.{system,user}.md`: the ten built-in prompt pairs, embedded at compile time;
- `model.zh-CN.toml`: everything else the model reads, such as tool descriptions, results, corrections, contract sections and fold labels.

The TOML is deserialized into `ModelText` with `deny_unknown_fields`; every entry is a `ResourceText`, a template parsed when loaded. Tests load it and render the texts with the values their callers pass.

`core::template` is the only template engine. Variables are `{{name}}` substitutions, scanned once, with no expressions. It renders the built-in prompts and their overrides, previews, user templates and resource text.

The effective prompt is the work's override, then the system's, then the built-in text (`store::prompts::PromptOverrides::effective`). Overrides are checked against their prompt's declared variables when saved. Contract sections, tool schemas and the stage material are appended by the agent, so an override cannot lose them.

## 11. Knowledge and vector search

There is no vector database. Each embedding model and vector size is a profile (`embedding_profiles`). Choosing a model in the settings makes its profile current and queues every live entry (`knowledge_indexes`, one row per entry and profile). Saving an entry queues it again.

The indexer takes the oldest pending task, splits the entry into chunks (`core::knowledge::chunks`) and embeds them. It stores each chunk with its vector as little-endian `f32` (`knowledge_chunks`). An outcome for an entry or profile that changed meanwhile is dropped. A profile becomes ready once the tasks queued when it became current are done; before that, search is refused with the number of tasks remaining.

Search (`store::search`) embeds the query once. It ranks, by exact cosine similarity, the chunks of live entries in the selected spaces whose index matches the entry's current revision under the current profile. At a single user's scale of about ten thousand chunks this is fast, deterministic and needs no extra service. Every embedding request is recorded for the dashboard.

## 12. Web UI

- **Data.** Every server read is a TanStack Query keyed in `api/queries/keys.ts`. Reads never go stale on a timer; events invalidate them (section 6). Revisions are immutable and cached forever. Mutations reuse a command ID until they succeed.
- **Drafts.** Unsent text (brief, guidance, feedback, review feedback, prompt edits) and citations are kept in `localStorage` per version and target until the server confirms them (`lib/drafts.ts`).
- **Previews.** Streaming previews arrive on the event stream without a sequence number and are held in `PreviewStore` until the workspace's in-flight request changes.
- **Citations.** Citable text is rendered in segments that name their target and offset. A selection is read across segments of one target only, and UTF-16 offsets are converted to Unicode scalar offsets (`features/workspace/citations.ts`).
- **Text.** Components never contain prose; they select catalog entries with typed selectors (`t(($) => $.area.key)`).

## 13. Adding a language

**An interface language.**
1. Add `webui/src/locales/<tag>/` with every namespace. Each file `satisfies Catalog<typeof en>`, so a missing or extra key fails type checking.
2. Collect the namespaces in `webui/src/locales/<tag>/index.ts` and add the catalog to `resources` in `i18n/index.ts`.
3. Add the tag to `UI_LANGUAGES`, with its own name in `UI_LANGUAGE_NAMES` (`locales/languages.ts`). Then teach `uiLanguageFor` which browser tags it serves. The Settings page lists `UI_LANGUAGES`.

**A writing language.**
1. Add a `WritingLanguage` variant in `core::project` with its serde and SeaORM value.
2. Name it in `model.zh-CN.toml` under `[languages]`; the name fills `{{writing_language}}` in prompts.
3. Add `crates/nekowriter-app/resources/export/<tag>.toml` and select it in `app::export::export_text`.
4. Label it in `webui/src/locales/*/common.ts` under `writingLanguage`.

The compiler points at every `match` on `WritingLanguage` that needs a new arm.

## 14. Tests

- **core and agent:** unit tests next to the code. Every model-text and export resource is loaded and rendered in tests.
- **store** (`crates/nekowriter-store/tests/`): integration tests per area against a temporary database. They drive runs by recording scripted answers through the store's own API.
- **app** (`crates/nekowriter-app/tests/`): the real server on a free port against `FakeModel`, a scripted Chat Completions and embeddings service. They cover whole flows: preparation, two-chapter novels, feedback and pauses, knowledge indexing and search, and the knowledge tool.
- **web UI:** Vitest with Testing Library and MSW, per page or component, in English. Fixtures are in `src/test/`.

The gate in the README runs everything in one pass, as CI does.
